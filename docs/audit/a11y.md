# dilekce accessibility audit (WCAG 2.2 AA)

Scope: `registry/dilekce/dilekce.tsx` (the registry item) and the demo at :5318.
Method: axe-core 4.x (wcag2a/2aa/21aa/22aa + best-practice) in edit, filled, after failed submit and after a blur error; light and dark; 1200px and 390px (16 runs). Plus ariaSnapshot, computed-style contrast (canvas-composited, alpha over real ancestors), Playwright emulation of forcedColors, reducedMotion, print, 600px/320px viewports (200%/400% zoom) and WCAG 1.4.12 text spacing.
Scripts and raw output: `/tmp/dilekce-audit/*.mjs`, `axe-results.json`, `forced-*.png`, `zoom-*.png`, `print.png`.

Priorities: P0 broken for real users, P1 gap most users hit, P2 worth having, P3 nice. Effort S/M/L.

## Summary

axe finds only three classes of issue in the item: `color-contrast` (light theme, invalid cells), `aria-allowed-attr` (filled mode, `aria-readonly` on `role=group`) and, in the demo only, `landmark-one-main`/`region`. Dark theme has no contrast violations. The bigger problems are ones axe cannot see: Windows High Contrast has no focus indicator and loses the grid and the checked state, blur errors are never announced, and the checkbox group's required state is not exposed.

---

## F1. Forced colors: no focus indicator, no cell borders, checked radio/checkbox indistinguishable

- Priority: **P1** (P0 for Windows High Contrast users). Effort: S-M.
- WCAG: 2.4.7 Focus Visible, 1.4.11 Non-text Contrast, 1.4.1.
- Evidence (Playwright `forcedColors: "active"`, screenshots `forced-focus.png`, `forced-choices.png`):
  - Focused text input: input `outline-style: none` (`outline-none` in `CONTROL_CLASS`, line ~1030), field `box-shadow: none`, background forced to Canvas. Result: only the caret shows; no indicator on the cell. The focus line is a `box-shadow` (line 599/608) and box-shadows are removed in forced colors.
  - The grid is drawn by `bg-border` showing through `gap-px`; backgrounds are forced to Canvas so every cell border disappears. Fields float as bare labels.
  - Radio/checkbox use `appearance-none` + `checked:bg-primary` + `shadow-[inset...]` (line 1400-1404). In forced colors a checked radio computes `bg: white; box-shadow: none`; checked looks identical to unchecked (screenshot). The checkbox tick svg (`text-primary-foreground`) also did not render visibly.
- Fix:
  - Field: `forced-colors:focus-within:outline-2 forced-colors:focus-within:outline-[Highlight] forced-colors:focus-within:-outline-offset-2` (or `outline-solid`), and `forced-colors:border` on the field cells so a 1px `CanvasText` border replaces the gap trick.
  - Marks: `forced-colors:checked:bg-[Highlight]` or `forced-colors:checked:border-[Highlight]` plus `forced-colors:checked:border-[6px]` for the radio (a thick border still works when shadows are stripped); for the checkbox keep the tick with `forced-colors:text-[HighlightText]` and `checked:bg-[Highlight]`.
  - Use `outline-hidden` (transparent outline) instead of `outline-none` where an outline would otherwise be the fallback.

## F2. Light theme: invalid, hovered and focused cells fail text contrast (11px labels and errors)

- Priority: **P1**. Effort: S.
- WCAG 1.4.3 (11px mono text, needs 4.5:1).
- Evidence (computed, composited): the tint classes `bg-destructive/5`, `hover:bg-accent/50` replace `bg-background` and are translucent, so the form's `bg-border` (#e5e5e5, the grid gap colour) shows through (line 599-601).
  - Invalid cell, label and error `#e7000b` on `#e5d9da`: **3.48:1**; invalid + hover 3.32; invalid + focus (`/10`) **3.18**. axe confirms (19 nodes in the failed state).
  - Hovered normal cell: label and any user placeholder `#737373` on `#ededed`: **4.05**.
  - Focused cell (opaque `bg-accent`, #f5f5f5): `n/max` counter `#737373`: **4.35**.
  - Dark theme: all pass (invalid 4.76-5.12, hover 5.98, counter 5.86).
- Fix: stop compositing over the grid colour. Use `bg-[color-mix(in_oklab,var(--destructive)_5%,var(--background))]` (same for the accent hover) or a `bg-background` base with a gradient layer (`bg-linear-to-b from-destructive/5 to-destructive/5`). Also darken light-mode counter/label on focus (the label already turns foreground; do the same for the counter).

## F3. Blur and live validation errors are never announced

- Priority: **P1**. Effort: S.
- WCAG 4.1.3 Status Messages (also 3.3.1 for non-sighted users).
- Evidence: the error `<span id=errorId>` (line ~893) is mounted conditionally, with no `role`/`aria-live`; the only live region is the form-level `role=status`, which is written only by a failed submit (line 525). Reproduced: fill Email with `x`, Tab away: error "Check format" appears, `role=status` text stays `""`. The error is only read if the user returns to the control (it is in `aria-describedby`). Same for the async "Checking…" and for a server `errors` prop update. Copy success ("Copied") is also silent.
- Fix: render a persistent, always-mounted `<span aria-live="polite" class="sr-only">` per field (or one in the form) and write `${label}: ${message}` into it on change; keep the visible span as is. Reuse the same region for `pending` and `copied`. Keep it polite and debounce live-as-you-type updates (the message follows the value live once shown).

## F4. Submit announcement and focus: correct, with caveats

- Priority: P3. Effort: S.
- Evidence: after a failed submit, focus goes to the first invalid control (`_r_0_`), whose `aria-describedby` includes its error ("Required"), and `role=status` reads "6 fields need attention" (`ariaSnapshot`: `status: 6 fields need attention`). The region exists before it is written (good), and the zero-width-space toggle (line 465) forces a repeat read. Caveats: some screen readers drop a polite update that lands in the same tick as a focus move; setting the text in a `requestAnimationFrame`/short timeout is more reliable. Only the first field's error is read; the count tells you more exist but not which (no list or links; 3.3.1 is met visually).
- Also: terse messages ("Check format", "Invalid step", "Too low") give no suggestion of what is expected (3.3.3, AA). Doc: pair them with `description` or let `messages` take functions (`min`/`pattern` known).

## F5. Checkbox group: `required` is not exposed; `aria-readonly` is invalid on `role=group`

- Priority: **P1** (required), P2 (readonly). Effort: S.
- WCAG 4.1.2, 3.3.2, 1.3.1.
- Evidence:
  - `DilekceCheckboxGroup` sets only `data-required` (line 1502). `aria-required` is not allowed on `role=group`, so assistive tech gets no "required"; the visible asterisk is CSS `content` with empty alt (`content-['_*'_/_'']`, line 817). A required checkbox group is silent to screen readers (the demo has none; the API supports it). Radio groups are fine (`aria-required` on radiogroup, `required` on each radio).
  - axe `aria-allowed-attr` in filled mode (all runs): `div[role=group]` has `aria-readonly="true"` (line 1506). Radiogroup and select are valid. Net effect: readonly state of checkboxes is not conveyed.
- Fix: put `aria-readonly` on each checkbox input (allowed on role=checkbox), not on the group; for required, add `aria-describedby` text "Required" (sr-only) or include it in the group name, or add `required` to the first checkbox is wrong (would force it), so use the sr-only text.

## F6. Stepper buttons: ambiguous names, tiny targets, down-event activation

- Priority: P2. Effort: S.
- Evidence: the accessibility tree lists `button "Decrease"` / `button "Increase"` three times in a row with no field context (`Weight`, `Pieces`, `Declared value`); defaults at lines ~1235. Size is 22x22 (measured), gap 2px; passes 2.5.8 only via the spacing exception, with zero margin (24px circles just touch neighbours); at `pointer-coarse` they are still 22px. They fire on `pointerdown` and start repeating (line 1350), so the action can't be cancelled by moving off before release (2.5.2 Pointer Cancellation, A; the repeat-on-hold is arguably essential, so unconfirmed as a failure).
- Keyboard alternative: yes. Tab skips the buttons (`tabIndex={-1}`), but the number input's ArrowUp/ArrowDown steps it (verified: Pieces 1 to 2). The buttons become `opacity:1` on `focus-within`/hover (verified after the 150ms transition). Acceptable; document that arrows are the keyboard path.
- Fix: default names built from the field label (`aria-label` = `${decrementLabel} ${label}` via `useField().labelId` + `aria-labelledby`), `size-6` (24px), fire the first step on `click`/pointerup and only repeat from pointerdown timers.

## F7. Copy button (filled mode): under 24px, hover-only look

- Priority: P2. Effort: S.
- Evidence: measured 49x18.3px (comfortable) and 47x17px (compact, 0px gap to the control). A 24px circle around it overlaps the control below by about 1-3px, so the 2.5.8 spacing exception doesn't clearly apply: marginal **fail** of 2.5.8 (AA). Name is good (`Copy Full name` via `aria-labelledby`), keyboard reachable (Tab order checked; becomes `opacity:1` on `focus-visible`), always visible at `pointer-coarse`, hidden when there's nothing to copy (display:none, so no empty buttons). "Copied" state swaps text but is not announced (see F3). Print: hidden (verified).
- Its focus outline is `outline-ring`: grey #a1a1a1 on white is 2.55:1 (under 3:1, same trap as the AGENTS.md note). The cell's own `--dk-focus` ring (filled mode, `has-focus-visible`) does show, so the combined indicator passes.
- Fix: `min-h-6 min-w-6`, `outline-(--dk-focus)` instead of `outline-ring`.

## F8. Radio/checkbox marks: 15px, own focus outline too light

- Priority: P2 (size P3). Effort: S.
- Evidence: inputs are 15x15, but each sits in a `<label>` that is the real target: 22.4px tall x 70-92px wide inline (16px apart), stacked at narrow widths 332-338 x 21-22.4 with a 6px gap. This passes 2.5.8 through target + spacing; compact density gives 21px height, still within the spacing exception. Unchecked mark border `#737373` on white = 4.74 (OK). `focus-visible:outline-ring` (line 1401) is 2.55:1 on light (fails 1.4.11 alone); in edit mode the cell's 2px primary line also shows, so the composite passes. Use `outline-(--dk-focus)`.

## F9. Affixes and counter are hidden from assistive tech

- Priority: P2. Effort: S.
- Evidence: `Affix` has `aria-hidden="true"` (line 1044), so `Weight` is exposed as `spinbutton "Weight": 1.5` with no "kg", and `Declared value` with no "$" (tree above). The `n/max` counter is `aria-hidden` (line 915): maxLength is still enforced natively, so nothing is lost, but the "near the limit" signal is not available either.
- Fix: add affixes to the control's `aria-describedby` (ids), or keep them visible to AT and rely on the sr text; for the counter, announce at 90% through the live region (F3).

## F10. Truncated labels and nowrap messages

- Priority: P3. Effort: S.
- WCAG 1.4.4, 1.4.10, 1.4.12.
- Evidence: labels are `overflow-hidden text-ellipsis whitespace-nowrap`. At 600px (200%) and at 1200 with 1.4.12 text spacing: no clipping, no horizontal scroll. At 320px (400%) with errors showing: `Postcode` label truncated (81>47). The error text moves below the control when long (the `data-below` measure) but the label itself is not given room. Text-spacing at 320px overflows only in the demo's segmented controls (right edge 347px), not in the item.
- Fix: let the label wrap when an error is present (`group-data-invalid/field:whitespace-normal`), or put the error below when label+error don't both fit.

## F11. Motion

- Priority: P3. Effort: S.
- Evidence: no `motion-reduce:` anywhere in the item (grep). With `reducedMotion: reduce`: field `transition-duration: .15s` still runs; the `Checking…` text keeps `animation: pulse 2s`. Not flashing; the pulse runs only while an async rule is pending (could exceed 5s: 2.2.2 would then apply to the pulse). Add `motion-reduce:animate-none motion-reduce:transition-none`.

## F12. Required indicator, language, form name

- Priority: P3. Effort: S.
- The `*` is purely visual (CSS content, alt `''`); native `required` is exposed to AT (verified: every required input has `required`). No legend explains the asterisk for sighted users (3.3.2): add a one-line "* required" note in the demo/docs. With `messages={dilekceMessages.tr}` the page `lang` stays `en`, so Turkish messages are read with an English voice (3.1.2); document passing `lang="tr"` on the form. The `<form>` has no accessible name, so it is not a landmark; docs could suggest `aria-label`.

## F13. Demo-only issues (not the registry item)

- Priority: P3. Effort: S.
- `landmark-one-main` and `region` (22-38 nodes): no `<main>`; wrap content.
- `Segmented` uses `role=radio` buttons with no arrow-key or roving tabindex (13 tab stops before the form), and the inactive option text is `#737373` on `#f5f5f5` = **4.34:1** at 12px (axe, 4 nodes, light only). Use real radios or `aria-pressed` buttons, and `text-foreground/80`.

## What passes (evidence)

- Names/roles/states: every control has an accessible name from its `<label for>`; the radio and checkbox groups are `radiogroup`/`group` named by the label via `aria-labelledby`; the empty select placeholder is not exposed twice. `aria-invalid` set on controls and on both group types when invalid (`textbox "Full name" [invalid]`, `combobox "Contents" [invalid]`). `aria-describedby` = description and error ids, verified focus on first invalid control reads its error.
- Filled mode: inputs/textarea are `readOnly`; select has `aria-readonly` and key guard (Tab still works); radiogroup `aria-readonly`; no keyboard trap (full Tab sequence through the page ends at body, 40 stops max). Focus order = DOM order.
- Scrub label: pointer only, but 2.5.7 is met (ArrowUp/Down on the input, steppers). Click on the label still focuses the input through the native `label` (the scrub handler focuses it on pointerup).
- Contrast of resting states passes: label light 4.74, dark 7.66; legend 18:1; placeholder/affix/description/select-empty/filled dash 4.74 light, 7.66 dark; filled value 17.9; filled copy 4.74. Focus line `--primary` vs cell: 14+:1 light, high in dark; invalid focus line (destructive on tint) 3.18 light (just passes 3:1), 4.76 dark. Disabled state is exempt (label at opacity .55: 2.12 light, 3.01 dark).
- Reflow: 390px and 320px, no horizontal scroll from the item. Print: filled form prints clean (screenshot), actions/copy hidden, `break-inside-avoid` set. Unconfirmed: printing while `.dark` is active (the form forces `print-color-adjust: exact`, so it may print dark).
- No hover-only functionality is unreachable by keyboard: copy button shows on `focus-visible`, steppers on `focus-within`, arrows work on the input.
